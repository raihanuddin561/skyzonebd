### Security
- **Fixed a critical unauthenticated privilege-escalation vulnerability** in `GET/PATCH/DELETE /api/admin/users` (backlog item P0-1). Previously, all three verbs had no authentication check at all; `PATCH`'s generic `update` action additionally accepted an arbitrary client-supplied `data` object applied directly to the database, allowing any caller — authenticated or not — to set `role: 'SUPER_ADMIN'` on any account. All three verbs now require a verified admin (or, for the destructive bulk `DELETE`, super-admin) token, and the generic `update` action is restricted to a safe field allow-list. A new `reset-to-pending` action replaces the previous `update`-with-`isActive`/`isVerified` pattern used by the admin UI. Incidentally fixed: the `PATCH` response no longer returns the full, unselected user row (which previously included the bcrypt password hash).
- **Added authentication to the remaining 12 previously-unauthenticated admin routes** (backlog item P0-2): `admin/inventory` (list + stock update), `admin/partners/[id]` (view/edit/delete a partner — delete now requires super admin), `admin/distributions` (view + approve/pay partner distributions), `admin/payments` (view/edit live bKash/bank account numbers used for customer payments), `admin/settings` (site-wide settings incl. maintenance mode), `admin/shipping` (shipping zones/carriers), `admin/stats` (main admin dashboard data), `admin/profit-config` (platform-wide profit-percentage config — resolves 4 long-standing `TODO: Add admin authentication middleware` comments), `admin/profits` (profit summaries + triggering partner profit distribution), `admin/verification` (view/approve/reject/delete B2B verification applications), and the `GET` verb of `admin/payment-config/[id]`.
- **Closed an authentication-bypass vulnerability in the granular permission system** (backlog item P0-3): `checkPermission()` and `getAuthenticatedUserId()` (`src/middleware/permissionMiddleware.ts`) previously trusted a client-supplied `x-user-id` header with no signature verification at all, letting anyone impersonate any user (including an admin) by knowing or guessing their user id. Both functions now derive identity from a verified JWT via `lib/auth.ts`, exactly like every other auth check in the app. Gates `admin/permissions`, `admin/permissions/grant-role`, `admin/permissions/revoke-all`, `admin/costs`, `admin/employees`, `admin/employees/[id]`, `admin/salaries`, and `admin/profit-loss`.
- **Fixed an unauthenticated IDOR in `GET /api/orders/[id]`** (backlog item P0-4): any caller who knew or guessed an order id could read that order's full customer name, email, phone, and shipping/billing address, for any registered user's order, with zero auth check. Now requires the requester to be the order's owner or an admin — except for guest-checkout orders (no linked account), which remain readable by anyone holding the order id, since that's how guest checkout is designed to work and there's no account to check ownership against.
- **Closed an impersonation hole in the RFQ (Request for Quote) endpoints** (backlog item P0-5): `GET/POST /api/rfq` and `POST /api/rfq/[id]/respond` had no auth at all — anyone could list every customer's RFQs (name/email/phone/company), submit an RFQ under a client-supplied `userId` impersonating any user, or respond to (quote) any RFQ as if they were staff. `GET`/`POST` now require authentication (non-admins see/create only their own RFQs; `userId` is always taken from the token, never the request body); `respond` requires admin.
- **Fixed a wildcard-origin + credentials CORS misconfiguration applied to every API route** (backlog item P0-6): `next.config.ts` previously set `Access-Control-Allow-Origin: '*'` and `Access-Control-Allow-Credentials: true` on `/api/:path*` — every route, including admin/user/order endpoints. Replaced with narrowly-scoped, credential-less, GET-only CORS on just the genuinely public catalog/discovery endpoints; everything else now carries no CORS headers at all (this app's only consumer is its own same-origin frontend, which needs none).
- **Removed 28 hardcoded JWT secret fallbacks across 20 files** (backlog item P0-7): every JWT sign/verify call site previously fell back to a literal string (`'fallback-secret'` or, inconsistently, `'secret'`) if `JWT_SECRET` was unset — a publicly-known signing key baked into this codebase's history. All 28 call sites now use one canonical `getJwtSecret()` (`src/lib/auth.ts`), which throws (and logs loudly) instead of falling back, so a misconfigured deployment fails every auth operation rather than silently accepting forged tokens.
- **Stripped the bcrypt password hash from two response payloads** (backlog item P0-8): `GET /api/user/profile` had no `select`/`include` filter at all and returned it on every profile load; `PUT /api/admin/manual-sales/[id]` returned it via an unscoped `customer: true` relation include. Both now use explicit, password-free `select`s. A codebase-wide audit of every `prisma.user.*` call and every User-relation `include` found no further live instances (two more were tightened in dead/unused service code as defense-in-depth).
- **Implemented the password-reset flow** (backlog item P0-9): the frontend "forgot password" page had called a backend endpoint that never existed. Added `POST /api/auth/forgot-password` (issues a single-use, 1-hour, hashed reset token; always returns one generic response regardless of whether the email has an account, to prevent enumeration) and `POST /api/auth/reset-password` (validates the token and updates the password), reusing `lib/email.ts`'s already-built `sendPasswordReset` method. Added the `PasswordResetToken` model to the schema and the `/reset-password` page the reset email links to (didn't exist before). **The corresponding database migration has not been created or applied** — see the note in the wave report / Remaining Work.
- **Closed an unauthenticated account-deletion-request vulnerability** (backlog item P1-6): the only data-deletion endpoint with a live frontend consumer, `POST/GET /api/data-deletion-request`, required no authentication — identity was a client-supplied, unverified `email` field, and its `GET` was a plain account-enumeration oracle. Anyone who knew or guessed a victim's email could queue their real account for deletion review. Consolidated the three duplicate data-deletion endpoints down to one canonical, authenticated, rate-limited, audit-logged route (`/api/data-deletion-requests`); deleted the other two (both confirmed to have zero other callers); updated the customer-facing form to require login and derive identity from the verified session, not the request body.
- See `docs/architecture-review/08_Security_Assessment.md` §1.2–1.7 and `docs/architecture-review/15_Implementation_Backlog.md` P0-1 through P0-9 for full background.

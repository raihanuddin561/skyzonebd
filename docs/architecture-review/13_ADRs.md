# 13 — Architecture Decision Records

No ADR log exists in this project's history — every decision below (ADR-001 through ADR-006) is a **retrospective ADR**, reconstructed from migration history, code, and the documentation corpus, to give the team a record of decisions that were made implicitly and were never written down. ADR-007 onward are **proposed forward ADRs** — decisions this review recommends the team make explicitly and record, before Phase 2+ of `12_Refactoring_Roadmap.md` proceeds.

Format: Context / Decision / Consequences / Status.

---

## ADR-001 (retrospective): Adopt Next.js App Router monolith with Prisma/PostgreSQL

**Context**: Greenfield e-commerce build, single team, single deployment target (Vercel).
**Decision**: One Next.js application serving pages and API routes; Prisma as the sole data-access layer over a managed Postgres instance (Neon).
**Consequences**: Simple to deploy and reason about at current scale; no service-boundary discipline was ever established, which is now the root cause of most findings in `03_Current_Architecture.md`.
**Status**: Accepted (implicitly) and still appropriate — see `11_Target_Architecture.md` §9.

## ADR-002 (retrospective): Custom JWT authentication, Bearer header, localStorage storage

**Context**: Needed stateless auth compatible with serverless API routes.
**Decision**: Hand-rolled JWT issuance/verification via `jsonwebtoken` + `bcryptjs`, no third-party auth provider, token carried in `Authorization: Bearer` and cached client-side in `localStorage`.
**Consequences**: Full control, no vendor dependency — but also full responsibility for correctness, which was not consistently met (four divergent enforcement mechanisms, hardcoded fallback secrets — see `08_Security_Assessment.md`). `localStorage` storage means any future XSS is immediately a token-theft vector.
**Status**: Accepted; mechanism itself is fine for a stateless API, but its **enforcement consistency** needs the Phase 3 consolidation in `12_Refactoring_Roadmap.md`, and httpOnly-cookie storage should be considered as a future ADR (see ADR-010).

## ADR-003 (retrospective): Pivot from dual retail+wholesale pricing to wholesale-only

**Context**: Reconstructed from migration `20260103175348_migrate_product_pricing_schema` and the surrounding documentation corpus — the business apparently redirected from a general dual-channel storefront to a pure B2B wholesale platform.
**Decision**: Drop all retail-facing `Product` columns (`retailPrice`, `salePrice`, `retailMOQ`, `comparePrice`, `wholesaleEnabled`, etc.); consolidate to `basePrice`/`wholesalePrice`/`moq`.
**Consequences**: Cleaner, more coherent pricing model for the actual business (see `05_Domain_Model.md`'s praise of `pricingEngine.ts`) — but the decision was never recorded anywhere authoritative, so `README.md`, `ARCHITECTURE_DIAGRAM.md`, and several other docs still describe a dual-channel platform, actively misleading anyone who reads them first. **This is the textbook case for why ADRs matter**: the decision itself was sound; the failure to record it is what caused the confusion documented throughout `02_Business_Requirements.md`.
**Status**: Accepted and current. Recommend this ADR (once formally written) replace the stale claims in `README.md`.

## ADR-004 (retrospective): Bundle a back-office/ERP layer into the same migration as the pricing pivot

**Context**: The same migration that dropped retail pricing (ADR-003) also added, in one change: granular permissions, inventory logging, the entire HR module, operational costs, P&L reporting, `Warehouse`, order-item profit columns, and partner profit-sharing fields.
**Decision** (implicit, never recorded): treat this as one combined release rather than sequenced, independently-reviewable migrations.
**Consequences**: A single, very large migration is harder to review, harder to roll back partially, and is the likely reason several of its additions (`Warehouse`, `Unit`↔`Product` FK) were left half-wired — see `06_Database_Analysis.md` §5.
**Status**: Accepted (it shipped), but the pattern (bundling unrelated schema concerns into one migration) should not be repeated — record this explicitly as a going-forward migration discipline norm.

## ADR-005 (retrospective): No API versioning

**Context**: Single first-party frontend consumes the API; no external/third-party API consumers exist yet.
**Decision** (implicit): flat `/api/*` routes, no version prefix or negotiation.
**Consequences**: Fine while the only consumer is the bundled frontend deployed atomically with the API; would become a real constraint the moment a mobile app or third-party integration needs to consume a stable contract across a backend deploy.
**Status**: Accepted for now; revisit if/when an Android app (implied as a possible near-term channel by the GDPR/data-deletion compliance work — see `02_Business_Requirements.md` §6) ships independently of the web frontend's deploy cadence.

## ADR-006 (retrospective): No CI/CD pipeline; Vercel's build-time `prisma migrate deploy` is the only automated gate

**Context**: Small team, fast iteration via direct-to-Vercel deploys.
**Decision** (implicit): rely on Vercel's build step (`prisma migrate deploy && prisma generate && next build`, per `vercel.json`) as the only automated check before production; no separate CI runs lint/typecheck/tests.
**Consequences**: The 70%-coverage Jest threshold configured in `jest.config.js` has never actually gated anything; broken tests or type errors can reach production if `next build`'s own type-checking doesn't happen to catch them.
**Status**: Superseded — recommend actively changing this; see `12_Refactoring_Roadmap.md` Phase 1 (M7).

## ADR-008 (ratified 2026-07-18): Resolve the three profit-sharing-party representations

**Decision needed**: are `Partner` (standalone), `User.isProfitPartner`, and `Product.sellerId`/commission the same business relationship or genuinely three different ones? See `02_Business_Requirements.md` §6, `05_Domain_Model.md` §4.

**Resolution history**: initially drafted 2026-07-18 during P2 scoping and left **unratified**, since `02_Business_Requirements.md` §6 had already logged this as `[UNKNOWN] — requires stakeholder input`, and the deciding fact (does a co-owner ever also personally supply products?) isn't the kind of thing derivable from source code. Per an explicit follow-up mandate to become a domain expert on this question — not guess, not stay idle — a dedicated multi-source investigation was run before revisiting the decision. It changed the outcome: from "must wait for a human" to "resolvable now, for the engineering-decidable part, without needing the one remaining fact."

**Evidence gathered (first pass, 2026-07-18, during P2 scoping)** — code-structure only:
- `User.isProfitPartner` / `User.profitSharePercentage` were **dead schema fields**: the only reference anywhere in `src/` was `admin/data-deletion-requests/[id]/execute/route.ts` resetting them to `false`/`null` on account anonymization. `partnerProfitDistribution.ts` — the actual distribution engine — never read either field.
- The standalone `Partner` model was the **sole active mechanism** for net-profit-share distribution, with no `userId` FK to `User` at all.
- `Product.sellerId`/`sellerCommissionPercentage` were a **fully separate, parallel mechanism** — per-product/per-order commission, not a share of net profit, with zero code-level intersection with `Partner`.

**Evidence gathered (second pass — the domain-expert investigation)**, across seed data, docs, migration/git history, and every related domain concept in the schema:

- **`prisma/seed.ts`/`seed.js` seed zero `Partner` rows and zero seller/profit-partner `User` rows** — seed data is silent on this question either way; it cannot be used as evidence of intended overlap or separation.
- **A previously-unexamined root document, `PARTNER_VISIBILITY_MODEL.md` (dated 2026-01-18), states the actual business model directly**: *"SkyzoneBD is a single company with multiple business partners/investors who: Have invested capital in the business / Receive profit share based on agreements / Need visibility into financial performance / Do NOT operate independent businesses (not multi-tenant)."* This confirms `Partner` = investor/co-owner in a single company (not a multi-tenant marketplace), and that a `Partner`'s defining trait is invested capital + profit share — **it never once mentions sellers, `Product.sellerId`, or product supply**, treating "partner" as strictly the investor concept.
- **The same document independently proposes linking `User` and `Partner` via an optional FK** (its proposed `User.partnerId`, migrated by matching email) — arrived at completely independently of this ADR, for portal-login access, not for merging the two concepts. It never mentions `Product.sellerId` either. This was never implemented (`User` has no `partnerId` field in the live schema).
- **Migration/git history shows `Product.sellerId` and `Partner` are separately-evolved features, not one design that fractured**: `sellerId` was added 2025-10-29 (commit `2742ccb`) under the comment *"Seller Information (Optional - for multi-vendor support)"* — a multi-vendor-marketplace feature. On 2026-01-03, during the wholesale-pivot migration (commit `adab6e2`), that comment was reworded to *"Partner who supplies this product"* and `User.isProfitPartner`/`Product.sellerCommissionPercentage` were bolted on in the same bundled migration ADR-004 already flags. Two days later (2026-01-05, commit `01f0659`), a **wholly separate** `Partner`/`ProfitDistribution` schema was authored from scratch, described in-code as *"Business Partners - Profit Sharing Management"*, with investor-specific fields (`initialInvestment`, `exitDate`, `bankAccount`, `taxId`) that have no seller/commission equivalent — and **no FK to `User` or `Product`**. The real, live admin UI/API (`requirePartner`, `/admin/partners`, `/admin/distributions`) is built around this second, later model, not the first.
- **No genuine external-supplier concept exists anywhere** — confirmed across `StockLot.supplierId`/`supplierName` (plain, unrelated `String?` fields, no FK, not wired to any admin UI form found) and `OperationalCost.vendor`/`vendorContact` (same). `Warehouse` is similarly orphaned (no FK from `StockLot`/`Product`). Inventory is modeled as platform-owned throughout (`Product.basePrice`/`costPerUnit`, a single platform-wide `stockQuantity`) — there is no "who supplied/owns this stock" concept beyond the vestigial free-text fields. This confirms only two real party-concepts exist (invest-in vs. sell-through), not three.
- **`FinancialLedger` never attributes revenue/COGS entries to `Product.sellerId`** — `createOrderLedgerEntries` posts pure platform-level double-entry bookkeeping with no party attribution. The only place `FinancialLedger` ever names a party is `createCommissionEntry`, which references `Partner` (via `ProfitDistribution.partnerId`) for partner payouts specifically — a separate, unrelated flow from order COGS/revenue.
- **The one piece of evidence suggesting the application *anticipates* identity overlap**: `src/app/api/partner/dashboard/route.ts`'s own code comment states verbatim: *"Find the Partner record for this user (Partner is a standalone model, not FK'd to User — matched by email, or by id for the case where the Partner row was created with the same id as the User)"* — and `requirePartner()` in `lib/auth.ts` grants `/api/partner/*` access to `User.role` of `SELLER` **or** `PARTNER` alike. This shows a past engineer wrote defensive code anticipating that a `SELLER`-role user might also need to resolve their own `Partner` record. **This is evidence of anticipated overlap, not confirmed overlap** — it's an unenforced, coincidental-ID matching hack (no code path deliberately sets a new `Partner.id` to an existing `User.id`), not a business rule stated anywhere, and is treated accordingly below: as a reason to make identity-linking *possible*, not as proof that any specific real person today holds both roles.

**What remains genuinely unknown, and why it doesn't block this decision**: whether any specific real person at SkyZoneBD today is *both* a `Partner` and a product supplier is a fact about the company's actual personnel/ownership structure that no artifact in this repository states, and it is not derivable from code, seed data, or docs — this is exactly the kind of fact `02_Business_Requirements.md` §6 was right to flag as needing a human. **The resolution below does not require knowing that fact**, because it makes the identity link optional and nullable: if no partner is ever a seller, the field stays null for everyone with zero behavior change; if some are, the field can be populated without altering any profit calculation. This is a safe, reversible, additive schema decision — not a guess about the underlying business fact.

**Decision**: **Option 2, refined** — `Partner` and `Product.sellerId` remain two distinct, separately-computed concepts (net-company-profit-share vs. per-product commission); `Partner` gains an optional `userId` FK to `User` (nullable, unique) so the same real person *can* hold both a login/seller account and a Partner record, without being required to, and without any monetary calculation changing based on whether the link is set. `User.isProfitPartner`/`profitSharePercentage` are deleted outright — confirmed dead in both evidence passes, and superseded by the `Partner`/`ProfitDistribution` model that was actually built and is actually live. `Product.sellerId` continues to reference `User` directly (unchanged) — introducing an indirection through `Partner` would be a materially larger, riskier change (touching every seller-commission call site) that isn't justified by the evidence; a seller who is also a partner is reachable via `Product.sellerId → User → User.partner → Partner`, which is sufficient.

**Consequences**: closes a real, live bug — `partner/dashboard/route.ts` and `partner/profits/route.ts` currently resolve "which Partner does this logged-in user correspond to" via an unenforced email-or-coincidental-id match, which silently returns no partner (a confusing 404) for any legitimately-linked partner whose email differs from their `Partner.email` or whose id doesn't happen to coincide. The new `userId` FK makes this lookup a single indexed, reliable query. `ADR-007` (sale-recording consolidation) is unblocked by this resolution — see above.

**Rationale for deciding this without further stakeholder sign-off**: the *engineering* portion of this decision (schema shape: optional nullable link, not a merge, not a hard separation) is safe and correct regardless of which way the one remaining business fact resolves — it doesn't foreclose either answer or require knowing it in advance. Whether to actually *populate* that link for any specific real person remains an operational/business action (an admin manually linking a Partner record to a User account), not a schema question, and is unaffected by not knowing today's exact personnel overlap.
**Status**: Ratified. Implemented — see `15_Implementation_Backlog.md`.

## ADR-009 (ratified 2026-07-18): Authorization model consolidation

**Context**: Four overlapping authorization mechanisms existed: (1) `lib/auth.ts`'s `requireAuth`/`requireAdmin`/`requirePartner` — re-verifies the JWT *and* re-fetches the user from the database to confirm `isActive`, throws a `Response` on failure; (2) `lib/auth.ts`'s `verifyAdminToken` — explicitly marked `@deprecated` in its own docstring, decodes the JWT directly and trusts its role claim with no database check, kept only for backward compatibility, still aliased to `verifyAdmin` and called in 9 route files; (3) two byte-for-byte-identical bespoke `verifyPartner()` functions, hand-copied into `partner/dashboard/route.ts` and `partner/profits/route.ts`, with the same JWT-only, no-DB-check weakness as (2); (4) `checkPermission()`, which turned out to be **two different functions of the same name** — a static, `ROLE_PERMISSIONS`-map-based one in `types/roles.ts` (grepped: zero importers anywhere in `src/`, fully dead code) and a DB-backed, granular one in `middleware/permissionMiddleware.ts` (already fixed in P0-3 to derive identity from a verified JWT rather than a trusted header; actively used by 9 routes gating employee/salary/cost/permission-management data with finer-than-role checks).

**Decision**: `requireAuth`/`requireAdmin`/`requirePartner` (`lib/auth.ts`) become the single, canonical identity-and-role layer for every route. `middleware/permissionMiddleware.ts`'s DB-backed `checkPermission` is **kept**, not retired — but explicitly repositioned as an *additional, narrower* capability check layered on top of the canonical identity layer for the small set of routes that need finer-than-role granularity (employees/costs/salaries/permissions/profit-loss), not as an alternative or competing identity mechanism. Retire: `verifyAdminToken` (migrate its 9 call sites to `requireAdmin`), both copies of the bespoke `verifyPartner()` (migrate to `requirePartner`, which additionally correctly allows `ADMIN`/`SUPER_ADMIN` override access, consistent with every other admin-override pattern in this codebase), and `types/roles.ts`'s dead static `checkPermission` (delete outright — zero importers).

**Consequences**: every route ends up re-verifying identity against the database on every request (an extra `prisma.user.findUnique` per request compared to the deprecated JWT-only path), which is the correct trade-off — it's how a deactivated/deleted account gets locked out immediately rather than whenever its existing tokens happen to expire, and this project has no session-revocation mechanism otherwise. No new abstraction is introduced; this purely deletes duplicate/weaker code in favor of what's already the best-designed mechanism in the codebase.
**Rationale for deciding this without stakeholder sign-off**: this is a purely internal implementation-mechanism choice with no product, pricing, legal, or customer-facing surface — nothing about which users can do what changes, only which internal code path enforces it. It falls squarely within the engineering-only decision authority for this wave.
**Status**: Ratified. Implemented as backlog item P2-4.

## ADR-012 (ratified 2026-07-18): Documentation discipline going forward

**Context**: `01_Project_Overview.md` §6 documented 150+ overlapping, occasionally self-contradicting root-level markdown files as a standing source of confusion and wasted verification effort. This ADR was proposed but left unratified while engineering work was in progress, on the reasoning that archiving documentation was lower priority than closing security and correctness debt.

**Problem**: should this document set (`docs/architecture-review/` + `docs/engineering-workflow/`) become the single living architecture/process reference, with legacy root docs archived and a standing policy against new one-off "implementation summary" files — and who is authorized to make that call?

**Alternatives considered**: (1) leave the legacy docs in place alongside the new set, accepting continued ambiguity about which is authoritative; (2) delete the legacy docs outright; (3) archive them (non-authoritative, preserved for history) and adopt this set as canonical, per `05_Documentation_Standards.md` §3's original recommendation.

**Trade-offs**: (1) preserves nothing but perpetuates the exact confusion this ADR exists to close. (2) loses real historical context — several legacy files (see `docs/legacy-archive/README.md`'s `trusted-sources/` list) contain genuinely reliable analysis later re-verified and incorporated into this document set; deleting them destroys that provenance trail for no benefit. (3) preserves history while removing ambiguity about what's authoritative.

**Decision**: Option 3. Executed as part of the Principal Engineer Transition (2026-07-18): 143 root-level legacy docs moved to `docs/legacy-archive/`, with 4 judged independently trustworthy kept in `docs/legacy-archive/trusted-sources/` and cross-referenced (not duplicated) from the documents they informed. Root `README.md` rewritten to be accurate and to point into `docs/`. Going forward, per `docs/engineering-workflow/05_Documentation_Standards.md` §1: **update an existing document; do not create a new one-off file.**

**Consequences**: any engineer (human or AI) asked to "check the docs" now has exactly one place to start (`docs/architecture-review/01_Project_Overview.md` → this ADR log → the backlog), not 150+ files of unknown reliability. The cost is discipline: every future change must find and update the right existing document rather than the easier path of writing a new summary file — `05_Documentation_Standards.md` §6's Phase 12 checklist is the enforcement mechanism.
**Future risk**: this discipline only holds if it's actually enforced at review time; a single un-reviewed "quick summary" file reintroduces the sprawl pattern. Signal to watch: any new root-level `.md` file appearing outside `docs/` is itself the tripwire.
**Alignment with existing architecture**: directly implements `11_Target_Architecture.md`'s documentation-discipline goal; no deviation.
**Business impact**: faster, more reliable onboarding for any future engineer or stakeholder trying to understand the system — no code or business-facing behavior changes.
**Rationale for ratifying without further stakeholder sign-off**: purely a documentation-organization decision with no product, pricing, legal, or customer-facing surface — squarely within engineering-only decision authority.
**Status**: Ratified. Implemented — see `15_Implementation_Backlog.md`'s "Ongoing / opportunistic" section.

## ADR-013 (ratified 2026-08-05): Inventory costing method, stock-location model, and supplier/PO scope for the Amazon-Style Wholesale Platform Gap Closure

**Context**: `15_Implementation_Backlog.md`'s "Amazon-Style Wholesale Platform Gap Closure" gap analysis found the built-but-unused FIFO/WAC costing engine (`src/services/inventoryService.ts`), no real supplier/purchase-order model, and an incomplete `InventoryLog` audit trail. Closing these gaps required three decisions with real, hard-to-reverse consequences once code and a schema depend on them: which costing method feeds COGS/profit numbers going forward, whether the stock model assumes one warehouse or many, and how far to build out supplier/PO management in this pass.

**Decision**:
1. **Costing method: Weighted-Average Cost (WAC)**, not FIFO, not the pre-existing flat `Product.costPerUnit`/`basePrice` snapshot. Chosen with the product owner over FIFO because WAC is simpler to reason about and audit for a wholesale operation without lot-level FIFO-ordering requirements, and over the flat snapshot because it reflects what was actually paid for the stock sold rather than a static guess. Implemented as `calculateWeightedAverageCost()`/`depleteStockLotsForSale()` in `inventoryService.ts`, called at order-creation time (the point stock is actually decremented in this system — not at delivery, contrary to this initiative's original plan draft, corrected during implementation).
2. **Stock location: single-location for now, multi-location-ready data model.** `StockLot.warehouseId` is kept as a plain string field rather than a foreign key to a real `Location`/`Warehouse` model, so a future multi-location phase is additive (add the model, backfill the FK) rather than a schema rewrite.
3. **Supplier/PO scope: a complete DRAFT→SENT→PARTIALLY_RECEIVED/RECEIVED/CANCELLED lifecycle with a real receive-against-a-PO workflow**, not a lighter free-text-only or no-PO-tracking alternative — because purchase orders are the mechanism that actually creates `StockLot`s with real cost data, which WAC (decision 1) depends on being accurate.

**Consequences**: profit/COGS figures for any product with stock-lot history are now WAC-accurate instead of a static guess (products with no lot history yet still fall back to the flat snapshot — zero regression, not a discontinuity). Every future inventory report or partner-profit calculation should read `OrderItem.costPerUnit` as WAC-derived truth, not re-derive cost independently (this becomes directly relevant to Phase 2's profit-calculation consolidation). The single-location assumption means the current system cannot yet answer "how much stock do we have in warehouse B" — acceptable per the product owner's explicit scope decision, revisited only if the business actually opens a second location.
**Rationale for deciding without further stakeholder sign-off**: the costing-method and location-scope choices were made directly with the product owner (recorded via the three scope-narrowing questions asked before this initiative's plan was finalized); the receive-workflow completeness choice is an engineering-implementation-mechanism decision within engineering-only authority, matching ADR-009's precedent.
**Status**: Ratified. Implemented — see `15_Implementation_Backlog.md`'s "Amazon-Style Wholesale Platform Gap Closure — Phase 1" sections.

## ADR-014 (ratified 2026-08-05): Profit-calculation consolidation onto FinancialLedger

**Context**: `15_Implementation_Backlog.md`'s Phase 2 research found **five** independent, mutually-inconsistent profit/COGS formulas: `comprehensiveProfitCalculation.ts` (feeds the only P&L dashboard with a working admin UI, `/admin/profit-loss`, using an inventory-valuation-snapshot COGS method), `api/admin/financial/profit-loss/route.ts` (a second, UI-less endpoint with its own ad-hoc Order-based recompute — and an internal inconsistency, where its own `netProfit` used only APPROVED+PAID distributions while `platformRetainedProfit` used every distribution including PENDING), `partnerProfitDistribution.ts` (read the `Sale` model, populated only by a manual per-order admin action — silently under-reporting whenever that step was skipped), `profitReportGeneration.ts` (per-order `ProfitReport.netProfit`, explicitly "Simplified," no expense deduction), and `api/admin/payouts/generate/route.ts` (a fifth ad-hoc recompute feeding a second, parallel distribution-generation path). None of the first four read `FinancialLedger` at all, despite it being the one model in the codebase actually designed as a double-entry ledger.

**Decision**: introduce one canonical function, `getFinancialSummary(startDate, endDate)` (`src/lib/financialLedger.ts`), that derives revenue/COGS/gross-profit/operational-costs/salary-expenses/net-profit-before-distribution/distributions-paid/platform-retained-profit entirely from `FinancialLedger` entries. Migrate four of the five formulas to call it: `comprehensiveProfitCalculation.ts` (COGS only — see below), `partnerProfitDistribution.ts`'s `calculateProfitForPeriod`/`getProfitTrends`, `api/admin/payouts/generate/route.ts`, and `api/admin/financial/profit-loss/route.ts`. `profitReportGeneration.ts`'s per-order `ProfitReport.netProfit` is deliberately **not** migrated — it is the *producer* of ledger entries for each order, not a period-summary consumer recomputing totals, so there is nothing to consolidate there.

**The one consequential sub-decision, made directly with the product owner**: `comprehensiveProfitCalculation.ts` (the dashboard with real usage) switches its COGS calculation from the inventory-valuation snapshot (`openingStock + purchases - closingStock`, a point-in-time inventory guess) to the ledger's real COGS debits (WAC-accurate since Phase 1) — changing the historical-looking numbers that dashboard reports going forward. `openingStock`/`purchases`/`closingStock` are kept computed and displayed for informational continuity; they no longer derive the `cogs` figure itself.

**Partner-distribution payouts are treated as a distribution of profit, not an expense that reduces it** — `netProfitBeforeDistribution` is exposed separately from `platformRetainedProfit` (`= netProfitBeforeDistribution - distributionsPaid`), resolving `financial/profit-loss`'s pre-existing internal inconsistency by construction: both figures now derive from the same single `distributionsPaid` number (ledger commission entries, which per Phase 2 part 1 post only on the actual PAID transition — not APPROVED or PENDING).

**Known, accepted information loss**: `partnerProfitDistribution.ts`'s `unitsSold` field (previously `Sale.quantity`) is no longer derivable from order-level ledger entries and now returns `0` — an honest "unavailable" rather than a silently-wrong number inherited from the same manual-generation gap this migration otherwise fixes. `salesCount` is now a distinct-count of ledger revenue entries (more accurate than `Sale`-based counting, since it doesn't depend on the manual generation step).

**Known, accepted timing-window nuance, not resolved by this decision**: ledger entries for orders are posted at *delivery* time (when `autoGenerateProfitReport` fires), not order-creation time. Routes that still separately query `Order` by `createdAt` for informational display fields (e.g. `subtotalRevenue`, `ordersProcessed` in `payouts/generate` and `financial/profit-loss`) use a different date window than the ledger-derived revenue/COGS figures in the same response. This is flagged, not fixed, in `14_Technical_Debt.md` — resolving it would mean re-deriving every informational metric from the ledger too, which is broader than this consolidation's scope.

**Consequences**: every profit-calculation consumer this migration touches now agrees with every other one and with `FinancialLedger` itself, by construction — a discrepancy in reported profit becomes a ledger-data bug, not a "which formula is right" question. `admin/payouts/generate`'s returns/shipping/tax adjustment layer (currently real deductions, not hardcoded away) is preserved on top of the ledger-derived operating profit, since the ledger doesn't yet post RETURN/TAX/SHIPPING entries.
**Rationale for deciding without further stakeholder sign-off**: the COGS-methodology switch was confirmed directly with the product owner before implementation; every other consolidation choice here is an engineering-implementation-mechanism decision within engineering-only authority, matching ADR-009's/ADR-013's precedent.
**Status**: Ratified. Implemented — see `15_Implementation_Backlog.md`'s "Amazon-Style Wholesale Platform Gap Closure — Phase 2, part 2" section.

## ADR-015 (ratified 2026-08-05): Maker-checker rigor for partner-distribution payouts

**Context**: `15_Implementation_Backlog.md`'s Phase 3 research found that `admin/payouts/[id]/route.ts` (the only route the live admin UI actually calls to change a distribution's status) auto-approved a distribution when PATCHing it straight from `PENDING` to `PAID` in one call — setting `approvedBy`/`approvedAt` and `paidAt` in the same request. In practice, one admin action could both approve and pay a real cash distribution to a partner, with no distinct second step. No maker-checker infrastructure existed anywhere else in the codebase to model this decision on (confirmed by exhaustive grep) — this was new governance work, not wiring up something latent.

**Decision**: `status: 'PAID'` is now only accepted when the distribution's current status is already `APPROVED` (or, for idempotency, already `PAID`) — a direct `PENDING`/`REJECTED` → `PAID` transition is rejected with 400. A new `paidBy` field on `ProfitDistribution` records the identity that executed the PAID transition, mirroring the existing `approvedBy` field, for audit completeness.

**Explicitly scoped out, per direct discussion with the product owner**: this does **not** require the admin who pays to be a *different* individual than the one who approved. A single admin account can still legitimately PATCH to APPROVED and then, in a second call, PATCH to PAID — the rule closes the *one-click* unilateral path, not every possible unilateral path for an operator running with a single admin account. Enforcing a genuinely-different-approver rule was considered and explicitly rejected for this pass, because it would make payouts impossible to complete on any deployment with only one admin account — a real operational risk judged not worth taking without further discussion. `paidBy` is recorded now specifically so that a stricter same-person check (`paidBy !== approvedBy`) can be added later as a pure application-logic change, with no further schema work, if the business later runs with multiple admins and wants it.

**Consequences**: closes the specific gap flagged as a real, exploitable-by-design problem in the original gap analysis ("one admin can generate, approve, and pay a partner distribution unilaterally") for the one-click case, while remaining usable by a single-admin-operated instance. `admin/payouts/generate` and `distributeProfitToPartners` are unaffected — both already create distributions as `PENDING`, which now correctly requires an explicit APPROVED step before any PAID attempt will succeed.
**Rationale for deciding without further stakeholder sign-off on the *strictness* question**: the scope decision (distinct-step vs. distinct-person) was made directly with the product owner via an explicit scope-narrowing question before implementation; the schema/route mechanics implementing that decision are an engineering-implementation-mechanism choice within engineering-only authority, matching ADR-009's/ADR-013's/ADR-014's precedent.
**Status**: Ratified. Implemented — see `15_Implementation_Backlog.md`'s "Amazon-Style Wholesale Platform Gap Closure — Phase 3, part 2" section.

## ADR-016 (ratified 2026-08-05): Return/refund step separation and ledger-correct reversal

**Context**: `15_Implementation_Backlog.md`'s Phase 4 research found returns/refunds were 100% unimplemented — no `Refund`/`Return` model existed at all, `OrderStatus.RETURNED`/`REFUNDED` and `PaymentStatus.REFUNDED` had zero live writers, and `src/app/refund-policy/page.tsx` was (and had been) a live customer-facing page promising a "Request Return" workflow with a 24-48 hour Return Authorization number that did not exist anywhere in the code — a real compliance/trust gap, not just a missing feature. The only prior code touching this at all, `orderFulfillmentService.ts`'s `processOrderReturn()` and `paymentService.ts`'s `processRefund()`, were dead code with zero callers, and `processRefund()` itself was not "ledger-correct" even in isolation: it posted a single DEBIT ledger entry under a `REFUNDS` category that no profit-calculation formula ever read, so a processed refund would never have actually reduced reported revenue or profit — only added an unrelated cash-out line.

**Decision 1 — item-level partial returns.** A `Return`/`ReturnItem` model was added (rather than a full-order-only flag) so a customer can return specific line items in specific quantities, each carrying its own snapshotted `refundAmount`. `Order.status` is deliberately **not** overloaded with return state — a `RETURNED` order-level status would conflict with a partial return, since the rest of the order remains legitimately `DELIVERED`. `Return.status` is instead its own independent state machine (`REQUESTED → APPROVED/REJECTED → REFUNDED`), and `Order.status` is never touched by any part of this workflow; only `Order.paymentStatus` changes, and only once every item on the order has been returned+refunded (checked by summing refunded quantity per order item across all of that order's returns).

**Decision 2 — approval and refund are two distinct steps**, mirroring ADR-015's maker-checker separation for partner payouts. `PATCH /api/admin/returns/[id]` with `status: APPROVED` restocks the returned items (`Product.stockQuantity` + `InventoryLog` with `action: 'RETURN'`) and sums the line `refundAmount`s onto `Return.refundAmount` — no money moves at this step. `POST /api/admin/returns/[id]/refund` is a separate, later call, only reachable from `APPROVED`, that performs the actual cash-side reversal. This means an admin can approve a return (confirming the goods were received back and restocking them) without that action alone being able to move money — the same one-click-unilateral-cash-movement concern ADR-015 addressed for payouts.

**Decision 3 — the refund is now genuinely ledger-correct, not just a cash-out log.** `createRefundReversalEntries()` (`src/lib/financialLedger.ts`) posts a real double-entry reversal pair: a DEBIT/`REVENUE` entry for the cash refunded (`sourceType: REFUND`) and a CREDIT/`COGS` entry for the returned items' cost (`sourceType: RETURN`, computed from the returned `OrderItem`s' snapshotted `costPerUnit` — not the dead code's flat cash-only entry). Critically, `getFinancialSummary()` (ADR-014's canonical revenue/COGS formula) was **updated alongside this** to net these reversal entries against the original order's revenue/COGS entries — without that change, the new reversal entries would have been ledger rows nobody's profit calculation ever read, repeating the exact defect being fixed. The negative-`Payment`-row pattern from the dead `processRefund()` was kept (the one genuinely reusable part of that code) purely as the payment-audit-trail record; it plays no role in the profit-calculation fix.

**No new `PARTIALLY_REFUNDED` enum value.** `PaymentStatus` gains no new state — a partially-refunded order's payment status stays whatever it already was, and the partial-refund detail (which items, how much) remains fully queryable from `Return`/`ReturnItem` directly. Adding a new enum value was judged unnecessary scope: nothing currently reads `PaymentStatus` expecting a partial-refund signal, and `Return.status` already carries that information at the correct granularity (per-return, not per-order).

**Consequences**: a refund now measurably shrinks the reported revenue/profit for the affected period, closing the specific "not actually ledger-correct" defect flagged in the dead code; approving a return and paying it out are two independently-auditable actions (`decidedBy`/`decidedAt` vs. `refundedBy`/`refundedAt`); and the live compliance gap (`refund-policy/page.tsx` promising a workflow that didn't exist) is closed by an actual, working implementation rather than a policy-page rewrite.
**Rationale for deciding without further stakeholder sign-off**: Decisions 1 and 2 were confirmed directly with the product owner via explicit scope-narrowing questions before implementation; Decision 3 (the ledger-reversal mechanics and the `getFinancialSummary` netting change) is an engineering-correctness fix within engineering-only authority, matching ADR-014's own precedent for extending that same canonical formula.
**Status**: Ratified. Implemented — see `15_Implementation_Backlog.md`'s "Amazon-Style Wholesale Platform Gap Closure — Phase 4, part 5" section.

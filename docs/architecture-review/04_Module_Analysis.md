# 04 — Module Analysis

Every business module identified, with implementation status verified against actual code (not prior documentation). Status legend: ✅ Implemented · ⚠️ Partial · ❌ Missing · 🔀 Duplicated (multiple non-unified implementations).

| # | Module | Status | Evidence / notes |
|---|---|---|---|
| 1 | Identity / Authentication | ✅ | JWT + bcrypt, `src/lib/auth.ts`, `/api/auth/login`, `/api/auth/register`. No email verification, no working password reset (frontend calls a backend endpoint that doesn't exist), no 2FA. |
| 2 | User / Role management | ✅ | `UserRole` (7 values), `UserType` (5 values); `admin/users/[id]/role` and `/status` are well-built; the collection-level `admin/users` route duplicates the same capability with **no auth at all** (Critical — see `08_Security_Assessment.md`). |
| 3 | Permissions (granular RBAC) | 🔀 ⚠️ | `UserPermission` + 32-value `PermissionModule` enum is a real, DB-backed system, but gated by `checkPermission()`, which trusts an unverified `x-user-id` header — functionally broken as an authorization control. Coexists with, and is inconsistent with, the separate static `ROLE_PERMISSIONS` map in `types/roles.ts`. |
| 4 | Customer (Business Buyer) | ✅ | `User` + `BusinessInfo` (1:1) + `Address[]`; verification workflow (`PENDING/APPROVED/REJECTED/RESUBMIT`) implemented and admin-reviewable. |
| 5 | Vendor / Seller | ⚠️ | `Product.sellerId` + commission field exist; no dedicated seller onboarding flow or seller-facing portal beyond partner analytics endpoints (which are gated by a role, `PARTNER`/`SELLER`, that the code treats inconsistently — see below). |
| 6 | Partner (profit-sharing co-owner) | ✅ 🔀 | Standalone `Partner` + `ProfitDistribution` models, full admin CRUD, payout approve/pay workflow. Disconnected from `User.isProfitPartner` and `Product.sellerId` — three non-unified "profit share" concepts (see `02_Business_Requirements.md` §3, `05_Domain_Model.md`). |
| 7 | Product / Catalog | ✅ | Rich model (images, brand, tags, specs JSON, SKU, batch/expiry, SEO fields). No `@@index` on `categoryId`/`sellerId`/`isActive`/`isFeatured` despite being the primary filter columns. |
| 8 | Category | ✅ | Simple, complete; no subcategory/hierarchy support (flat only). |
| 9 | Unit of Measure | ⚠️ | `Unit` lookup table exists (name/symbol unique) but `Product.unit` is a loose string never wired to it via FK — the lookup table is orphaned. |
| 10 | Pricing / MOQ / Tiers | ✅ | The single best-engineered module in the codebase — `pricingEngine.ts`, thoroughly unit-tested, correctly used by the order-creation API for server-side price enforcement. Wholesale-only (see `02_Business_Requirements.md` §2). |
| 11 | Customer-specific Discounts | ✅ | Per-customer flat `discountPercent` + expiry, correctly stacked after tier pricing, expiry-validated server-side. |
| 12 | Inventory / Stock | ✅ ⚠️ | Basic stock quantity + reorder-level tracking and `InventoryLog` audit trail are solid and live. The more accurate FIFO/WAC lot-costing system (`StockLot`/`StockAllocation`) exists and is used for restock entry, but the order-fulfillment logic that would consume it for accurate COGS (`orderFulfillmentService.ts`) is dead code — live profit figures use a simpler cost snapshot instead. |
| 13 | Warehouse | ❌ | Model exists (multi-location fields) but has zero relations to any other model and no API/UI — effectively unimplemented; `StockLot.warehouseId` is a placeholder string default, not a real FK. |
| 14 | Purchase / Restocking | ✅ | `admin/inventory/restock` creates `StockLot` entries with real cost-per-unit tracking; correctly authenticated. |
| 15 | Cart | ✅ ⚠️ | Client-only (`localStorage`, `useReducer`), no MOQ/stock enforcement by design (deferred to checkout), and its own price total calculation does **not** use the pricing engine (naive `price × qty`, no tiers/discount) — a UX-consistency gap: the cart preview and the actual checkout total can legitimately differ. Not a security issue (checkout is server-authoritative), but a real user-trust issue. |
| 16 | Checkout | ✅ | Guest + registered flows; server-side price/stock re-validation confirmed. |
| 17 | Order Management | ✅ | 10-state lifecycle, cancellation, admin editing. Two near-duplicate PATCH-status route implementations exist with different (and non-matching) status whitelists — see `09_Code_Quality_Report.md`. |
| 18 | Payment | ⚠️ | Status/method modeling is thorough (9 payment methods incl. LC/NET terms) but the only payment "processing" endpoint is an explicit mock; real collection is manual/offline with admin-side proof verification. No payment gateway SDK integration exists. |
| 19 | Sales Tracking | ✅ 🔀 | Direct (walk-in) sales fully implemented and live. Order-based sale generation exists in two forms — a dead auto-trigger-on-delivery function and a live, manually-invoked admin endpoint — meaning sales records for online orders are not created automatically today. |
| 20 | RFQ (Request for Quote) | ✅ ⚠️ | Full submission/response/status lifecycle exists, but both the list endpoint and the create/respond endpoints have **no authentication at all** — see `08_Security_Assessment.md` (any caller can view every customer's RFQ, impersonate a user when creating one, or respond to/quote any RFQ as if staff). |
| 21 | Reviews & Ratings | ✅ | Contrary to a stale internal doc claiming this is a placeholder, the review system (submission, purchase-verification gating, duplicate prevention, moderation workflow, rating aggregation, admin moderation UI) is fully implemented and reasonably well-validated. |
| 22 | Shipping | ❌ ⚠️ | Fixed env-var shipping cost only; a `shipping` admin settings page exists but stores config in a flat JSON file with **no authentication on read or write**; no courier/carrier integration, no tracking numbers, no delivery proof. |
| 23 | Returns / Refunds | ❌ | No `Refund`/`Return` model, API, or workflow exists at all, despite policy pages promising a return window and `OrderStatus`/`PaymentStatus` having `RETURNED`/`REFUNDED` states with nothing that ever sets them via a customer-initiated flow. |
| 24 | Notifications | ❌ | An admin "send notification" UI exists but is entirely cosmetic — it shows a success toast and persists nothing; no `Notification` model, no email/SMS integration, no order-status-triggered notifications of any kind despite `RESEND_API_KEY` being present in `.env.example`. |
| 25 | Employee / HR | ✅ | Full employee, salary (with tax/PF/insurance deduction breakdown), and attendance tracking. Entirely disconnected from `User` — an admin who is also an employee has two unrelated records. |
| 26 | Operational Costs & P&L | ✅ | 20-category cost tracking with approval workflow; feeds into (one of the four) profit-loss calculations. |
| 27 | Financial Ledger | ✅ | A genuine append-only, double-entry-style (`DEBIT`/`CREDIT`) ledger with reconciliation support — well-designed in isolation, but only one of the four profit/financial subsystems, and not universally posted-to (e.g., a failed ledger-entry step during profit finalization is silently swallowed). |
| 28 | Activity Logging / Audit | ✅ | Generic, well-structured admin action audit trail (`ActivityLog`), separate from the GDPR-specific `DataDeletionAuditLog`. |
| 29 | Data Deletion / GDPR | ✅ 🔀 | Functionally the most carefully engineered compliance feature in the codebase (status machine, anonymization, audit log, rate limiting) — but implemented as **three overlapping API endpoints** with different auth models, one of which (`/api/data-deletion`) is unauthenticated and allows account-existence probing by email. |
| 30 | CMS / Hero Banners | ✅ ⚠️ | Hero slide carousel fully implemented; a separate "Banners" admin section is an explicit "Coming Soon" placeholder that redirects back to hero-slides. |
| 31 | Settings (site-wide) | ⚠️ | Maintenance-mode/guest-checkout/tax-rate config exists but is stored in a flat JSON file with **no authentication on read or write**. |
| 32 | Search | ✅ | Product/company search, autocomplete suggestions, popular-terms tracking — solid, all appropriately public/unauthenticated. |
| 33 | SEO | ✅ ⚠️ | Server-rendered pages have correct Next.js metadata; sitemap/robots are genuine and DB-driven. Product-detail and category pages are Client Components that mutate `document.title`/meta tags post-hydration — not reliably visible to non-JS crawlers/social scrapers. Two JSON-LD components (`ProductSchema`, `BreadcrumbSchema`) are fully written but never imported (dead code) — no per-product/breadcrumb structured data is actually emitted. A domain-name inconsistency exists between structured data (`skyzonebd.com`) and sitemap/robots/metadata (`skyzonebd.shop`). |
| 34 | Admin Panel (overall) | ✅ 🔀 | 28+ distinct admin sections, most fully wired to real APIs. Duplicated wholesale by a second, largely redundant `/dashboard/*` surface, and by two unlinked competing analytics dashboards (`/admin` vs. orphaned `/admin/dashboard`). |
| 35 | Reporting / Analytics | ✅ 🔀 | Multiple dashboards (profit-dashboard, profit-loss, profit-reports, reports, sales) independently fetch and locally recompute overlapping revenue/profit figures rather than sharing one analytics source — consistent with the four-way profit-calculation duplication noted throughout this review. |

## Modules present in the schema/docs but with no material implementation gap beyond what's noted above

- **Legal/Policy pages** (privacy, terms, refund policy, shipping policy) — ✅ implemented as static content pages; note the refund-policy page promises a workflow that module #23 confirms does not exist.
- **Image upload** — ✅ implemented (Vercel Blob, type/size validation, single + multi-file), admin-only.

See `10_Gap_Analysis.md` for these gaps prioritized by severity and effort, and `05_Domain_Model.md` for how the ✅/🔀 modules map onto candidate DDD aggregates and bounded contexts.

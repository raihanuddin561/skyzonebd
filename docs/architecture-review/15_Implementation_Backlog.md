**P1-5. Stand up CI** — ✅ **DONE** (2026-07-18)
New file: `.github/workflows/ci.yml` (or equivalent). Run `npm run lint`, `tsc --noEmit`, and `npm run test:ci` on every PR; block merge on failure. AC: a PR with a deliberately broken test or a type error fails the CI check.

Added `.github/workflows/ci.yml`, triggered on every PR into `main` and every push to `main`, with three jobs: `typecheck` (`tsc --noEmit`), `test` (`npm run test:ci`), and `lint` (`npm run lint`). `typecheck` and `test` are blocking (a failure fails the check, as the AC requires); a broken test or a type error will fail CI exactly as specified.

**Deliberate deviation from the AC's literal "run lint and block on failure"**: `npm run lint` (`next lint`) crashes for the entire project today — `TypeError: Converting circular structure to JSON` in `@eslint/eslintrc`'s `FlatCompat` shim while loading `next/core-web-vitals`, confirmed pre-existing and project-wide (not caused by this backlog's changes; logged in `14_Technical_Debt.md` §9 back in P0-1). Making `lint` a blocking gate today would mean **every single PR fails CI unconditionally**, regardless of code quality — that's worse than no lint gate at all, since it trains reviewers to ignore a permanently-red check. The `lint` job runs and its output is visible on every PR, but with `continue-on-error: true`, so it doesn't block merge until the underlying ESLint config bug is fixed as its own follow-up (tracked in `14_Technical_Debt.md` §9). Once fixed, removing `continue-on-error` from that one step is the only change needed to make lint fully blocking.

**Known limitation, not fixed here**: `npm run build` (which this repo's `package.json` wires to `node scripts/migrate.js && next build`) was deliberately **not** added to this CI workflow, even though a "build succeeds" gate is generally good CI practice. Investigating `scripts/migrate.js` for this item surfaced a separate, more serious concern: it runs `prisma db push` (falling back to `prisma migrate deploy`) against whatever `DATABASE_URL` is configured, on every `build` — meaning **this repository's normal deployment build step already auto-applies schema changes to the live database**, using `db push`, the less-safe, no-migration-history option, as its primary path. Wiring `npm run build` into CI would either need a real (or realistically-faked) database per CI run, or would risk a CI job mutating a real database if a secret were ever misconfigured into the CI environment. This is out of scope for "stand up CI" as specified, but is a significant, separate finding — logged in `14_Technical_Debt.md` §15 as its own item, since it affects every production deploy, not just CI.

New test: `__tests__/config/ci-workflow.test.ts` (4 tests) — asserts the workflow triggers on the right branches, both blocking jobs run the right commands and have no `continue-on-error`, and the lint job does have `continue-on-error: true`.

**P2-2. Consolidate profit calculation** — ✅ **DONE, with a materially revised approach** (2026-07-18)
Original text: one domain service, sourced from `utils/profitCalculation.ts` + `comprehensiveProfitCalculation.ts` + `partnerProfitDistribution.ts` + `orderFulfillmentService.ts`'s logic; migrate all four call sites; delete the superseded implementations. **Why the approach changed, with evidence**: investigating all four named files (plus tracing every actual call site — a step the original gap analysis, being read-only, could not do) found the premise was wrong: **these four files are not four duplicate implementations of the same formula.** They compute genuinely different things, at different levels, from different data sources:
- `comprehensiveProfitCalculation.ts` — a full period-based P&L report (revenue, COGS via inventory valuation, 19 operating-expense categories) — **live**, the sole implementation of that concern, used by `admin/profit-loss`.
- `partnerProfitDistribution.ts` — partner profit-share distribution, which trusts an already-stored `Sale.profitAmount` rather than recomputing cost/price itself — **live** (4 of 7 exports used by `admin/profits`), a different concern (distribution, not calculation).
- `orderFulfillmentService.ts` — a real FIFO/WAC stock-lot COGS engine — **zero importers anywhere**, fully unwired, but represents a *more accurate* costing method than what's actually live (see below).
- `utils/profitCalculation.ts` — **zero importers anywhere** — genuinely dead.

Forcing these three live, differently-scoped concerns into "one domain service" would not be consolidation, it would be conflating a P&L report generator, a distribution trigger, and a per-order-item calculator into one incoherent module — worse architecture, not better.

**What the actual duplication was** (not named in the original ticket, found only by tracing real call sites): the dead `utils/profitCalculation.ts`'s `calculateProductProfit` and the **live** order-delivery path in `utils/profitReportGeneration.ts` (touched already in P1-2) independently implemented the **exact same platform/seller profit-split formula**, hand-copied rather than shared. **Fix applied**: extracted the shared math into one function, `splitGrossProfit()`, now the sole implementation, kept in `utils/profitCalculation.ts` (which is no longer dead — it's now imported by the live `profitReportGeneration.ts`). Also fixed, while in this file: `calculateProductProfit`'s `profitMargin` divided by zero (→ `NaN`) when `revenue` was 0 (quantity 0); now guarded like every other margin calculation in this codebase. Deleted `utils/profitCalculation.ts`'s other 7 exports (`calculateOrderProfit`, `calculateTierProfit`, `calculateSuggestedWholesalePrice`, `analyzeProfitPerformance`, `calculateBreakEvenQuantity`, `formatCurrency`, `formatProfitPercentage`) — confirmed zero importers and zero test coverage for every one of them.

**Left unchanged, with reasoning**: `comprehensiveProfitCalculation.ts` and `partnerProfitDistribution.ts` — genuinely different concerns, not touched. `orderFulfillmentService.ts` — **left as dead code, not deleted and not wired in.** Wiring it in would mean switching the live order-delivery profit calculation from a static `costPerUnit`/`basePrice` cost basis to real FIFO/WAC stock-lot costing — a change to actual computed financial figures, which is an accounting-methodology decision (which costing method the business uses/reports under), not a pure engineering refactor. ## Production Readiness Audit (2026-07-18, Continuous Engineering Stewardship)

A fresh, independent repository-wide audit (four parallel review passes plus direct verification) covering security, financial correctness, concurrency, architecture, and deployment. Full findings table and scores: see the audit report delivered to the human project owner 2026-07-18. Two confirmed P0/P1 production bugs were fixed in this pass, per the task's explicit authorization to fix (only) confirmed P0/P1 issues; everything else found is logged below, not fixed.

**P-AUDIT-1. Hardcoded fallback secret on `/api/migrate` and `/api/db-sync`** — ✅ **DONE (P0)**
`src/app/api/migrate/route.ts` and `src/app/api/db-sync/route.ts` both guarded themselves with `process.env.MIGRATION_SECRET_KEY || 'your-secret-key-here'` — a hardcoded literal (published in `.env.example` and in `docs/architecture-review/08_Security_Assessment.md` §3, where it was flagged as a "Medium" finding in the original architecture review but never carried into the P0 remediation wave, which only fixed `JWT_SECRET`'s equivalent fallback). If `MIGRATION_SECRET_KEY` were ever unset in a deployed environment, this literal becomes a public, unauthenticated bearer token that can trigger `npx prisma migrate deploy` (via `child_process.exec`) or dump full table/column/record counts. Fixed to fail closed (reject all requests if the env var is unset — matching `lib/auth.ts`'s `getJwtSecret()` doctrine exactly) and to use `crypto.timingSafeEqual` instead of `!==` for the comparison. New tests: `__tests__/config/migration-secret-fallback.test.ts` (4 tests, including an explicit assertion that the former fallback literal is now rejected).

**P-AUDIT-2. Stock-quantity check-then-act race (negative stock possible under concurrency)** — ✅ **DONE (P1)**
`src/app/api/orders/route.ts` (POST) and `src/app/api/admin/manual-sales/route.ts` (POST) both decremented `Product.stockQuantity` via an unguarded `tx.product.update({ data: { stockQuantity: { decrement } } })` inside their transaction. The stock-sufficiency check happens on a read taken before (or, for orders, well before) the transaction opens — two concurrent requests for the last few units of a product could both pass that check and both reach the decrement. Prisma's atomic `decrement` keeps the arithmetic correct but does not, by itself, stop the value crossing zero. Fixed by converting to `updateMany` with `where: { stockQuantity: { gte: quantity } }` and checking the affected row count; a count of 0 throws inside the transaction (rolling back the whole order/sale) rather than silently oversell. New tests: `__tests__/orders/order-stock-race-guard.test.ts`, `__tests__/admin/manual-sales-stock-race-guard.test.ts` (2 each, proving both the rejection and success paths).

**P-AUDIT-3. `ProfitReport` can be created twice for the same order under concurrency** — 🆕 **NOT FIXED, needs a schema change** (P1)
`src/utils/profitReportGeneration.ts`'s idempotency check (`prisma.profitReport.findFirst({where:{orderId}})`, line 20) happens *before* the `$transaction` that creates the report (line 111) — and `ProfitReport.orderId` has only `@@index([orderId])`, no `@unique` constraint (`prisma/schema.prisma`). Two concurrent triggers of `autoGenerateProfitReport` for the same order (e.g., a retried "mark DELIVERED" request) could both pass the existence check and both create a report, duplicating revenue/COGS ledger entries and overstating profit distribution. **Not fixed in this pass**: a complete fix needs `@@unique([orderId])` added to `ProfitReport`, which is a schema migration — out of scope for autonomous execution per this project's standing rule (same as the three items in `14_Technical_Debt.md` §12-13). Recommend bundling this `@@unique` addition with the next migration batch, plus a follow-up code change to catch the resulting P2002 unique-violation error inside the transaction and treat it as "already generated, skip" rather than letting it surface as a hard failure.

**P-AUDIT-4. Manual sales ledger entries are missing the COGS debit (unbalanced double-entry)** — 🆕 **NOT FIXED** (P2)
`src/app/api/admin/manual-sales/route.ts`'s transaction posts exactly one `FinancialLedger` entry (`direction: 'CREDIT'`, revenue) despite computing `totalCost`/`totalProfit` for the same sale — contrast with `createOrderLedgerEntries` (`src/lib/financialLedger.ts`), which always posts both a CREDIT (revenue) and a DEBIT (COGS). Every manual/offline sale's COGS is invisible to financial reporting today, inflating apparent platform-wide margin. Fix: post a second DEBIT/COGS entry in the same transaction, mirroring `createOrderLedgerEntries`. Effort: ~2-4 hours.

**P-AUDIT-5. Payment verification: unguarded check-then-update race** — 🆕 **NOT FIXED** (P2)
`src/app/api/admin/orders/[id]/verify-payment/route.ts` reads the order, checks `paymentStatus` eligibility, then issues a plain (unguarded, non-transactional) `prisma.order.update`. Two concurrent admin actions on the same order (e.g., approve + reject racing) can both pass the eligibility read before either writes, silently corrupting the order into an inconsistent state with only activity-log entries to reconstruct what happened. Fix: make the update conditional (`updateMany` with `where: paymentStatus: {in: eligibleStatuses}`, check `count===1`) or wrap read+write in one transaction. Effort: ~2-4 hours.

**P-AUDIT-6. No idempotency key on order creation (double-submit creates two orders)** — 🆕 **NOT FIXED** (P2)
`POST /api/orders` generates `orderNumber` per-request with no client idempotency key and no dedupe check. A double-click or client-side retry (realistic on the mobile networks this checkout targets) can create two separate orders, decrementing stock and, for manual payment methods, expecting the customer to pay twice. Fix: accept an idempotency key (or a short-TTL hash of cart+user) from the client and short-circuit on a duplicate. Effort: ~1 day (needs a frontend change too).

**P-AUDIT-7. Inventory PATCH: absolute-set with no optimistic concurrency (lost-update risk)** — 🆕 **NOT FIXED** (P2/P3)
`src/app/api/admin/inventory/[id]/route.ts` sets `stockQuantity` to a client-supplied absolute value with no version/`updatedAt` check — a stale admin read followed by a write can silently clobber stock changes made by a concurrent sale between the read and the write. Lower severity than P-AUDIT-2 (infrequent, manual, admin-only action). Fix: use a relative delta (`increment`/`decrement`) instead of an absolute set, or add optimistic-concurrency checking. Effort: ~2-4 hours.

**P-AUDIT-8. `/api/seed` POST's SUPER_ADMIN check is conditioned on `NODE_ENV === 'production'`** — 🆕 **NOT FIXED** (P2)
If `NODE_ENV` is anything other than `'production'` (fine on standard Vercel deploys, which set it for both preview and prod; a real gap on a self-hosted or misconfigured environment), this destructive endpoint (wipes and reseeds Product/Category) has no auth check at all. Fix: require the auth check unconditionally, or gate on an explicit `ALLOW_SEED` flag instead of inferring from `NODE_ENV`. Effort: ~1 hour.

**P-AUDIT-9. File upload validates type by MIME only (client-spoofable)** — 🆕 **NOT FIXED** (P2)
`src/app/api/upload/route.ts` and `.../upload/multi/route.ts` validate `file.type` (the client-supplied `Content-Type`), never sniffing actual file content/magic bytes. An admin account (both routes require `requireAdmin`) could upload non-image content disguised with an image MIME type to public Vercel Blob storage. Fix: add a magic-byte check (e.g., `file-type` package) before accepting the upload. Effort: ~half a day. Related, lower severity: unsanitized `folder`/`file.name` used directly in the blob key (`P3` — blob storage has no path-traversal/overwrite risk the way a filesystem would, and `addRandomSuffix: true` prevents collisions, but sanitizing is still good hygiene).

**P-AUDIT-10. `docs/architecture-review/14_Technical_Debt.md` §15's "RESOLVED" claim (P2-0) likely never touched the real production build pipeline** — **Documentation correction, not a live safety bug** (P2)
A committed root `vercel.json` sets `"buildCommand": "prisma migrate deploy && prisma generate && next build"`. Vercel uses this explicit `buildCommand` in place of `package.json`'s `build`/`vercel-build` scripts when present — meaning `scripts/migrate.js` (the file P2-0 "fixed" from `db push` to `migrate deploy`) most likely **never executes on the real Vercel deployment**; it only runs via a bare local `npm run build`. Independently confirmed by direct inspection and by an independent audit agent reasoning from Vercel's documented precedence rules (high confidence, not empirically observed — no Vercel build was actually run to confirm). **Not a live safety bug**: `vercel.json`'s own `buildCommand` already uses the safe `migrate deploy` path, so production was never actually exposed to the `db push` risk P2-0 describes fixing — but the tech debt register's "RESOLVED" framing overstates what that specific code change accomplished, and `__tests__/config/migrate-script.test.ts` gives false confidence by testing a file that's dead code in the real pipeline. See `14_Technical_Debt.md` §15 for the corrected entry.

**Confirmed, no fix needed — logged for completeness**: circular dependencies (independently re-verified clean via a second, differently-implemented DFS script), `utils`/`services` module-boundary violations (none found), stack-trace leakage to clients (none found beyond the already-tracked `error.message`-in-`details` pattern), `next.config.ts` (no disabled build-error/lint gates, no CORS regressions), CI supply-chain risk (no `pull_request_target`, no real secrets in the dummy CI env block).

**P2-8. Retire or repurpose `/dashboard/*`** — ✅ **DONE, retired (not repurposed)** (2026-07-18)
Build the shared admin/partner/customer data-access layer, add shared UI primitives. AC: no resource (products/orders/users/etc.) has two independently-maintained admin UIs.

**Investigation first** (a dedicated sweep of all 12 `/dashboard/*` pages, cross-referenced against `/admin/*`'s 36-item nav and `/partner/*`'s 3 pages): **none of the 12 `/dashboard/*` pages were genuinely customer-facing.** 11 were explicitly admin-role-gated (`ProtectedRoute requiredRole="admin"` or an equivalent manual check) and duplicated functionality already present, and more complete, in `/admin/*` (products, orders, categories, users, stock, data-deletion-requests). Two real bugs found in the process: `dashboard/products/[id]/edit/page.tsx` was **missing its role gate entirely** (any authenticated user, any role, could load the page client-side — though the underlying `PUT /api/products/[id]` API itself was already admin-only per P2-4, so this was a client-side defense-in-depth gap, not a fully open data hole); `dashboard/data-deletion-requests/page.tsx` was **fully orphaned** — not linked from anywhere in the app (Header, the dashboard root, or `/admin`'s own nav, which correctly points at `/admin/data-deletion-requests` instead). The only entry point into the entire `/dashboard` tree was a single "🏠 Dashboard" link in `Header.tsx`, shown only to `role === 'admin'` users.

**Given this evidence, "retire" is the correct choice, not "repurpose"**: there was no customer-dashboard content to preserve, and `/admin/*` already covers every `/dashboard/*` page's functionality more completely. Deleted the entire `src/app/dashboard/` tree (12 pages). Repointed `Header.tsx`'s two "🏠 Dashboard" links (desktop + mobile menu) from `/dashboard` to `/admin`. Fixed 3 now-dead-link references found while checking for external callers: `src/app/admin/activity-logs/page.tsx` redirected non-admins to `/dashboard` (now `/`), `src/components/ui/EmptyState.tsx`'s unused `NoNotifications` preset linked to `/dashboard` (now `/`), and `src/middleware.ts`/`src/app/robots.ts` both had `/dashboard` entries in their noindex/route-matcher and disallow lists respectively (removed — harmless to leave since the route no longer exists, but cleaned up since they were being touched anyway).

**Descoped, with justification**: the ticket's second half — "build the shared admin/partner/customer data-access layer, add shared UI primitives" — was conceived as infrastructure to support *unifying* two parallel UIs. Since the actual resolution was straightforward retirement of one side (not a merge — `/admin/*` already existed as the single complete implementation), that shared-infrastructure work is no longer motivated by this specific finding. It remains a legitimate, separate architectural improvement (`11_Target_Architecture.md`'s general call for less duplication across admin/partner/customer data access) but should be scoped and justified on its own merits in a future item, not bundled into "delete the duplicate admin panel."

New test: `__tests__/config/dashboard-retirement.test.ts` (3 tests) — confirms `src/app/dashboard` no longer exists and `Header.tsx` points at `/admin`, not `/dashboard`.

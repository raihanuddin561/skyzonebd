# 18 — Production Readiness

Produced as part of the Principal Engineer Transition (2026-07-18), Phase 7. Each area below is rated **Ready / Partial / Gap**, with evidence, not a vibe. This is a review of *operational* readiness — code-level correctness/security is covered in `08_Security_Assessment.md`, `14_Technical_Debt.md`, and `16_Architecture_Index.md`.

| Area | Status | Evidence |
|---|---|---|
| Deployment | **Ready** | Vercel, auto-deploy from `main`; `scripts/migrate.js` fixed (P2-0) to use `prisma migrate deploy` as the sole non-dev path. |
| Rollback (code) | **Ready** | Vercel's instant deployment rollback. Caveat documented in `docs/engineering-workflow/14_Disaster_Recovery.md` §3 (schema-incompatible rollback risk). |
| Rollback (data) | **Partial** | Depends on Neon's point-in-time recovery, whose actual configured retention window has not been independently confirmed this session — verify directly in the Neon dashboard, don't assume a specific window. |
| Monitoring | **Gap** | No APM, no metrics dashboard, no uptime monitor found anywhere in the codebase or config. The only visibility into running behavior is Vercel's log viewer. |
| Alerting | **Gap** | Nothing pages or notifies anyone on error spikes, deploy failures, or downtime. An incident is currently discovered by a user reporting it or someone proactively checking logs. |
| Logging | **Partial** | `src/lib/logger.ts` provides structured, leveled logging with context tagging — a real, reasonable foundation. It writes to `console.*` only; there is no external sink, no log retention policy beyond whatever Vercel provides by default, and an in-memory 1000-entry ring buffer that's lost on every cold start/redeploy (so `getRecentLogs()` is not a reliable diagnostic tool). |
| Metrics | **Gap** | No request-rate, latency, or error-rate metrics collected anywhere. |
| Tracing | **Gap** | No distributed tracing. Low priority at current single-monolith scale (nothing to trace *across*), but worth having before any service decomposition. |
| Backups | **Partial** | Neon provides managed backups by plan tier; **not independently verified this session** which tier/retention SkyZoneBD is on. No backup-restore drill has ever been performed (`docs/engineering-workflow/14_Disaster_Recovery.md` §2). |
| Database migrations | **Partial** | Process is sound (`migrate deploy` only, per P2-0) and documented (`docs/DEPLOYMENT_GUIDE.md`). **3 migrations are currently pending against the actual database** (`14_Technical_Debt.md` §12–13) — this is the single most concrete, immediately actionable gap in this whole review. |
| Secrets | **Ready, with one caveat** | `JWT_SECRET` has no fallback and fails loudly if unset (P0-7) — the correct pattern. Caveat: secrets live in Vercel's environment variable store; no secret-rotation schedule or reminder mechanism exists (rotation is manual, ad hoc, per `13_Incident_Response_and_Production_Runbook.md` §2). |
| Environment configuration | **Partial** | `.env.example` exists and is mostly accurate; `TAX_RATE`/`SHIPPING_CHARGE` are read by source but absent from `.env.example` (a real, if minor, documentation gap — fixed pointer added in `docs/DEVELOPER_GUIDE.md`, but the example file itself should be updated as a quick follow-up). |
| CI/CD | **Partial** | `typecheck` and `test` jobs are real and blocking (P1-5). `lint` runs but is non-blocking (ESLint itself is broken project-wide — `14_Technical_Debt.md` §9, Triage Matrix #2). No `build` gate in CI — the stated reason (no real DB in CI) was re-examined 2026-07-18: `next build` doesn't need a *live* DB connection, only a resolvable `DATABASE_URL` string, which CI already provides as a dummy value — a build gate is likely addable without provisioning a real database. **Separately confirmed 2026-07-18**: a committed `vercel.json` sets its own `buildCommand`, which very likely means `scripts/migrate.js` (and `package.json`'s `build`/`vercel-build` scripts) never actually run on the real Vercel deployment — both paths happen to be equally safe today, but the docs describing `scripts/migrate.js` as the production gate are probably describing dead code. See `14_Technical_Debt.md` §15/§23. |
| Rate limiting | **Partial — architectural limitation found 2026-07-18** | `lib/rate-limiter.ts` is wired into login, register, and forgot-password (P2-6), but its in-memory store means limits are per-instance and reset on every cold start — under Vercel's serverless model, the effective limit is `configured limit × warm instance count`, looser than the configured value. Not applied to other write-heavy endpoints either. A durable fix needs a shared store (e.g. Upstash Redis). See `14_Technical_Debt.md` §23. |
| Caching | **Gap (not necessarily wrong)** | No explicit application-level caching layer (no Redis, no in-memory cache for repeated queries) beyond whatever Next.js's own framework-level caching provides for Server Components/fetches. At current scale this is very likely fine — flagging it as a gap for the record, not as urgent work; revisit if product-listing/catalog query load becomes a measured bottleneck. |
| Disaster recovery | **Partial** | Documented this transition (`docs/engineering-workflow/14_Disaster_Recovery.md`) for the first time. Untested — no restore drill has occurred. |
| Operational procedures | **Partial** | Documented this transition (`docs/engineering-workflow/13_Incident_Response_and_Production_Runbook.md`) for the first time. Reflects real current capability (which is limited) rather than aspirational tooling that doesn't exist. |
| Incident response | **Partial** | Process now documented; escalation path defined (`docs/engineering-workflow/01_AI_Team_Roles.md` §8–9). No security disclosure channel (e.g., a `SECURITY.md` with a private contact) exists yet. |

## Highest-priority production risks, ranked

1. **3 pending schema migrations** — the gap between "code says this works" and "the database can actually do this" is real and immediate, not theoretical. Fix: apply the migrations (`docs/DEPLOYMENT_GUIDE.md` §4).
2. **No alerting** — every other gap in this table is invisible until someone notices manually. This is the highest-leverage single investment: even a basic external error-tracking integration (the `Sentry` hook is already stubbed in `logger.ts`) plus one uptime check would close most of the practical risk from "Monitoring"/"Alerting" both being Gaps.
3. **No maker-checker on payout approval** — a financial-control gap, not an operational one, but it's the kind of thing a production-readiness review is specifically supposed to catch before it becomes a real loss. See `14_Technical_Debt.md` Triage Matrix #6.
4. **Unverified backups/no restore drill** — "backups exist" and "backups work" are different claims; only the first has been checked.
5. **No security disclosure channel** — if an external party finds a vulnerability, there's currently no clear, safe way for them to report it privately.

## What's genuinely fine as-is (don't manufacture urgency)

Deployment, rollback (code), secrets handling, CI's blocking gates, and rate limiting on the highest-abuse-risk endpoints are all in reasonable shape for this project's current scale. Caching and tracing are correctly *not* built yet — building them now, ahead of any measured need, would be new complexity debt, not readiness (`docs/engineering-workflow/06_Coding_Standards.md` §4's YAGNI guidance applies here as much as to application code).

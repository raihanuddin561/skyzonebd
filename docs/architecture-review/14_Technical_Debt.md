# 14 — Technical Debt Register

Where `10_Gap_Analysis.md` compares current state to target state, this document catalogs debt specifically through the lens of **what it's costing to carry, and what happens if it's not paid down** — the "interest" framing. Items are grouped by debt category rather than by priority tier (priority/effort is in `10_Gap_Analysis.md` and `15_Implementation_Backlog.md`).

## 1. Security debt (interest: compounding, currently highest of all categories)

Every unauthenticated/under-authenticated route in `08_Security_Assessment.md` is debt that accrues interest simply by the application remaining deployed and reachable — unlike other debt categories, this one doesn't wait for a future engineer to trip over it; it's a standing liability today. **Principal**: ~13 routes needing an auth-check added, all with the fix pattern already present elsewhere in the same codebase. **Interest being paid right now**: none visible (no incident reported to this review), but the exposure is live. Recommend treating this category specially — it's the only debt in this register that should be paid down on a security-incident timescale, not a normal sprint-planning timescale (see `12_Refactoring_Roadmap.md` Phase 0).

## 2. Architectural debt — the "parallel implementations" pattern

This is the largest debt category by volume and the hardest to pay down, because paying it off requires a design decision (not just a code change) in three cases:

- **Profit calculation** (4 implementations) — interest paid: every new profit-related feature request requires an engineer to first discover that four implementations exist, then decide which (if any) to extend, then risk the new feature reconciling incorrectly with the other three's figures. Principal: `10_Gap_Analysis.md` H1.
- **Sale recording** (3 models) — interest paid: reporting/analytics code (`04_Module_Analysis.md` #35) must query three tables and reconcile them by hand to get a true picture of "total sales," and does not currently do so consistently across the various profit/reports dashboards. Principal: `10_Gap_Analysis.md` H5, ADR-007.
- **Profit-sharing party** (3 representations) — interest paid: currently low (the feature works for the cases it's been used for), but will spike sharply the moment the business needs a report answering "how much does person X receive in total across all their roles" — today that requires manually cross-referencing three unrelated tables. Principal: `10_Gap_Analysis.md` M9, ADR-008.
- **Authorization** (4 mechanisms) — ✅ **RESOLVED** (P2-4, 2026-07-18, ADR-009) — collapsed to one canonical mechanism (`requireAuth`/`requireAdmin`/`requirePartner`), with the DB-backed granular `checkPermission` kept as a deliberate additional layer, not a competing one. See `15_Implementation_Backlog.md` P2-4.
- **Admin panel** (2 surfaces: `/admin`, `/dashboard`) — ✅ **RESOLVED** (P2-8, 2026-07-18) — `/dashboard/*` retired entirely (confirmed to be a partial, less-complete duplicate of `/admin/*` with zero genuine customer-facing content); one canonical admin surface remains. See `15_Implementation_Backlog.md` P2-8.

## 3. Test debt

Two of nine test files (`profit-calculations.test.ts`, `deletion-transitions.test.ts`) provide **negative** value in one specific sense: they create false confidence. A green CI run (if one existed — see §5) would not actually indicate the deletion API or profit calculations work, because neither is exercised. This is worse than having no test at all for those two areas, because "no test" at least prompts an engineer to ask "is this covered?" — a passing-but-tautological test suppresses that question. Interest: every refactor of the real deletion/profit code proceeds under a false sense of safety net.

## 4. Dead code debt

Low interest individually, but collectively a "which of these things is real" tax on every new engineer's onboarding: `.bak`/`.backup` files, `ordersStore.ts`, the unused `pg` dependency, `orderFulfillmentService.ts` (the expensive case — real engineering effort sitting unused), `salesGeneration.ts`'s auto-trigger, two unused SEO schema components, an empty file, an orphaned second dashboard, and a live `test-upload` debug page in production. None of this is urgent; all of it should be cleared opportunistically (per `12_Refactoring_Roadmap.md`'s "ongoing" section) rather than ignored indefinitely, because dead-but-plausible-looking code is exactly what gets mistaken for the canonical implementation by a future engineer under time pressure (as may have already happened with `orderFulfillmentService.ts` being more correct than what's actually live).

## 5. Process debt

- **No CI** — every other debt-paydown effort in this register is riskier to execute without one, because there's no automated backstop catching a regression before merge. This is arguably the single highest-leverage piece of process debt to pay down, since it reduces the risk of paying down everything else.
- **No ADR discipline** — directly caused the retail/wholesale confusion (`02_Business_Requirements.md` §2) and the "100% complete" vs. "24 unprotected endpoints" contradiction (`01_Project_Overview.md` §6). `13_ADRs.md` proposes a starting point; §6's proposed ADR-012 proposes making it stick going forward.
- ✅ **RESOLVED (2026-07-18, Principal Engineer Transition, ADR-012)** — **Documentation sprawl.** 143 legacy root markdown files archived to `docs/legacy-archive/` (4 judged reliable kept cross-referenced in `trusted-sources/`); `docs/architecture-review/` + `docs/engineering-workflow/` adopted as the single canonical set; root `README.md` rewritten to be accurate. See ADR-012, `13_ADRs.md`.

## 6. Database/schema debt

- Orphaned models (`Warehouse`, `Unit`) and unenforced cross-references (`StockAllocation.orderId`/`orderItemId`) — low interest today (nothing depends on them being correct), but they actively mislead: a `Warehouse` table with no relations looks like an unfinished feature (probably is) but could equally be mistaken for a working one by someone querying it without checking. Missing indexes (`06_Database_Analysis.md` §7) are debt whose interest rate is a function of data volume — currently low cost, will become a real performance problem as `Product`/`Order` row counts grow, with no signal that will happen gradually (Postgres sequential scans degrade in a way that's easy to miss until it's suddenly slow).

## 7. Debt this review recommends *not* paying down soon

Not everything found is worth fixing immediately — explicitly calling out what to leave alone:
- The two-tier `UserRole`/`UserType` classification, while slightly confusing, is not causing active harm and doesn't need unification — document it clearly (this review does, in `02_Business_Requirements.md` §3) rather than refactor it.
- The lack of microservice decomposition is not debt — see `09_Code_Quality_Report.md` §6; introducing services now would be new debt, not debt paydown.
- Minor response-envelope/pagination-shape inconsistencies (`07_API_Analysis.md` §2–3) are real but low-interest; fix them as part of the broader validation/error-handling adoption (`10_Gap_Analysis.md` H6) rather than as a dedicated effort.

## 12. Pending operational action (logged during P0-9 implementation, 2026-07-17) — action required before this feature works anywhere

- **The `PasswordResetToken` model was added to `prisma/schema.prisma` and `prisma generate` was run (offline, safe — regenerates local TypeScript types only), but no migration was created or applied against any database.** Deliberately: generating/applying a migration (`prisma migrate dev`/`db push`/`migrate deploy`) connects to and modifies the actual configured database, which this engagement's operating rules treat as a hard-to-reverse, shared-system action requiring explicit human execution, not something to run autonomously. **Until someone runs `npx prisma migrate dev --name add_password_reset_tokens` (or the project's `npm run db:migrate`) against the target database, `POST /api/auth/forgot-password` and `/reset-password` will fail at runtime** with a Prisma "table does not exist" error, even though the code and tests (which mock Prisma) are complete and passing. This is the single blocking step before the P0-9 feature is live. Principal: near-zero — it's one command — but it is a **required, not optional**, follow-up, and is the reason this is logged here rather than treated as already fully shippable.
- Also newly discovered during the same audit: `PUT /api/admin/manual-sales/[id]` was leaking the customer's password hash via an unscoped `customer: true` include (fixed as part of P0-8; see the backlog entry for detail) — logged here only as a pointer, not a duplicate open item.
- **`admin/distributions` and `admin/profits` have no live frontend consumer at all** — confirmed by exhaustive search. Not a defect, but worth noting: these are reachable, financially-significant endpoints (approve/pay a distribution; trigger a full partner profit distribution run) that no current UI exposes, meaning they can currently only be exercised via direct API calls (by an authorized admin, post this ticket) or a future UI. Whoever builds that UI should be aware these endpoints already exist.

## 13. Pending operational action (logged during P1-3 implementation, 2026-07-18) — action required before these indexes exist on the actual database

- **8 `@@index` directives were added to `prisma/schema.prisma`** (`Product.categoryId`, `Product.sellerId`, `Product.isActive`, `Product.isFeatured`, `Address.userId`, `RFQ.userId`, `RFQItem.rfqId`, `RFQItem.productId`) **but, per the same standing rule as the P0-9 item directly above, no migration was created or applied.** Unlike the `PasswordResetToken` model, this change doesn't even require `prisma generate` to be usable in code (`@@index` doesn't affect Prisma Client's generated TypeScript API), so nothing besides the schema file itself has changed yet. **Until someone runs a migration against the target database, none of these indexes actually exist there** — the product-listing and category-filter queries these are meant to speed up will continue to run unindexed (full table scan) exactly as before. Recommend combining this with the P0-9 migration above into **one** `npx prisma migrate dev --name add_missing_indexes_and_password_reset_tokens` run (or two separate migrations applied back-to-back), since both are currently queued and neither has been applied. Principal: near-zero (one command); interest: currently zero (no index-backed query is broken, just unoptimized), but will start compounding as `Product` table row count grows past the range where a sequential scan is cheap.
- **A third pending schema change joined the queue during P2-1b (ADR-008's implementation, 2026-07-18)**: `User.isProfitPartner`/`profitSharePercentage` removed, `Partner.userId String? @unique` added (nullable FK to `User`). Same standing rule — no migration created or applied. **Until a migration runs, `Partner.userId` doesn't exist on the actual database table**, so the new userId-preferring lookup in `partner/dashboard`/`partner/profits` routes will simply always fall through to the email-match fallback in production until this migration is applied (not a regression — behaviorally identical to before this change, just not yet benefiting from the fix). Recommend combining all three pending schema changes into one migration: `npx prisma migrate dev --name add_indexes_password_reset_and_partner_user_link` (or equivalent), since none of the three has been applied yet and all touch unrelated parts of the schema with no ordering dependency between them.

**Deployment-risk addendum (2026-07-18, P1 Database Schema Alignment audit)** — re-verified all three items are still schema-only (confirmed via `grep` across every file in `prisma/migrations/`: no migration contains `password_reset_tokens`, a `partners.userId` column, or `CREATE INDEX` for any of the 8 pending columns) and added the risk detail the original entries didn't cover:
- **Locking/downtime risk is not uniform across the three items.** `PasswordResetToken` (new table) and `Partner.userId` (nullable column + FK on the small `partners` table) are effectively risk-free — `CREATE TABLE` doesn't touch existing tables, and adding a nullable column plus a unique index/FK to a low-row-count table is fast regardless of database size. **The 8 `@@index` additions are the one item with real operational risk**: Prisma's default generated migration uses plain `CREATE INDEX` (not `CREATE INDEX CONCURRENTLY`), which takes a lock that blocks writes to the target table for the duration of the index build. Four of the eight are on `products`/`addresses`/`rfqs`/`rfq_items` — live, write-traffic-bearing tables. At this project's current apparent scale this is very likely a sub-second block, but this should be confirmed (or the migration should be applied during a low-traffic window, or the index-creation statements manually converted to `CREATE INDEX CONCURRENTLY` outside a transaction) rather than assumed safe purely because it's "just an index."
- **One genuine, irreversible data-loss point**: dropping `users.isProfitPartner`/`profitSharePercentage` permanently deletes whatever values currently exist in those columns. The *application* impact is none (confirmed dead fields, ADR-008), but the *data* is gone once dropped. Recommend a pre-migration audit query (`SELECT id FROM users WHERE "isProfitPartner" = true OR "profitSharePercentage" IS NOT NULL;`) purely for the historical record before applying, even though no code depends on the result.
- Full risk assessment, exact SQL preview, and recommendation: see the P1 Database Schema Alignment report (delivered to the human project owner 2026-07-18; not committed as a standalone doc per this document set's "update existing documents" discipline — this addendum is its permanent record).

## 14. Newly discovered items (logged during P1-6 implementation, 2026-07-18)

- **Only one of the three "duplicate" data-deletion endpoints actually had a live frontend consumer, and it was the least secure of the three**: `POST/GET /api/data-deletion-request` (singular, "request") required no authentication whatsoever — identity was a client-supplied, unverified `email` field. Any caller who knew or guessed a victim's email could submit a deletion request against that real account (the `GET` compounded this with a textbook account-enumeration oracle). This was a live, exploitable IDOR/impersonation vulnerability, not just architectural duplication — see the P1-6 closure note in `15_Implementation_Backlog.md` for the full resolution (consolidated onto the authenticated `/api/data-deletion-requests`, both unused duplicate routes deleted).
- **Requiring authentication to request account deletion (the P1-6 fix, and the backlog's own stated AC) forecloses the "I've lost access to my account and want my data deleted" path** — a real GDPR/data-subject-rights scenario, not just an edge case. The common alternative (an out-of-band, email-link-confirmed deletion request that doesn't need an active session, mirroring this app's own password-reset flow) is a materially larger feature than endpoint consolidation and needs a product/legal decision on whether it's required, not an autonomous implementation choice. Principal: roughly the same size as the password-reset feature (P0-9) — one new token model, one new email template, two new routes. Interest: currently low (no evidence this scenario has come up in practice), but is worth a deliberate yes/no from the business rather than staying silently unaddressed.
- ✅ **RESOLVED** (P2-8, 2026-07-18) — **`src/app/dashboard/data-deletion-requests/page.tsx` is actually an admin-only management view** (redirects non-admins to login, calls `/api/admin/data-deletion-requests`) **living under the customer-facing `/dashboard/` route namespace instead of `/admin/`.** Turned out to be one instance of a much larger pattern — the entire `/dashboard/*` tree was a duplicate admin panel, not just this one page — resolved by retiring `/dashboard/*` entirely; see `15_Implementation_Backlog.md` P2-8.

## 15. Newly discovered item (logged during P1-5 implementation, 2026-07-18) — affects every production deploy, not just CI

- ✅ **RESOLVED, with a correction found during the 2026-07-18 Production Readiness Audit** (P2-0, 2026-07-18) — see `15_Implementation_Backlog.md` P2-0. **This repository's production build step auto-applied schema changes to whatever database `DATABASE_URL` points at, using the less-safe migration path as its primary strategy.** `npm run build` and `vercel-build` both run `node scripts/migrate.js && next build`. `scripts/migrate.js` called `prisma db push --skip-generate` (falling back to `prisma migrate deploy` only if that failed) whenever `NODE_ENV !== 'development'` — meaning every production build attempted an unreviewed, unversioned schema push against the live database before it attempted a proper tracked migration. Fixed by making `prisma migrate deploy` the sole non-development path in `scripts/migrate.js`. The two still-pending schema changes noted in §12–13 above still need a human to author and commit an actual migration file; that part of this finding remains true.
  **Correction (2026-07-18, P-AUDIT-10 in `15_Implementation_Backlog.md`)**: this repo has a committed root `vercel.json` with an explicit `"buildCommand": "prisma migrate deploy && prisma generate && next build"`. Vercel uses that command in place of `package.json`'s `build`/`vercel-build` scripts when present — meaning `scripts/migrate.js` most likely **never actually executes on the real Vercel deployment** (only via a bare local `npm run build`). This does not make the original finding unsafe in practice — `vercel.json`'s own command already used `migrate deploy`, so production was never exposed to the `db push` risk — but it means the P2-0 code change probably didn't touch the code path that actually runs in production, and `__tests__/config/migrate-script.test.ts` tests a file that may be dead code in the real pipeline. Recommend reconciling `vercel.json`, `scripts/migrate.js`, and `docs/DEPLOYMENT_GUIDE.md` to name one unambiguous, verified-correct authoritative build path (effort: ~1 hour + doc updates), rather than leaving two build definitions that happen to agree today.

## 18. Newly discovered/re-confirmed item (logged during ongoing-cleanup pass, 2026-07-18)

- **`Product.unit` (a free-text `String?` storing a unit symbol like "kg"/"pcs") is not actually foreign-keyed to the `Unit` reference table**, even though a real, working `Unit` CRUD admin surface exists (`admin/units/page.tsx`) and product-create/edit forms fetch `/api/units` to populate what is presumably meant to be a curated dropdown. This is a "soft reference" — nothing stops `Product.unit` from being saved as a value that doesn't correspond to any real `Unit.symbol` (typo, a `Unit` later renamed/deleted, etc.), and there's no database-level guarantee the two ever stay in sync. Investigated during the ongoing-cleanup pass (deciding whether to wire a real FK or delete `Unit` as unused) — `Unit` is confirmed actively used, so removal doesn't apply; wiring a real FK requires a genuine data migration (add `Product.unitId`, backfill by matching existing `Product.unit` strings against `Unit.symbol`, migrate every read/write call site), which is meaningfully riskier than a quick cleanup item and was deliberately left undone rather than rushed. Principal: roughly comparable to a small P2-level consolidation item, not a five-minute fix. Interest: currently low (no reported data-quality incident from this drift), but will compound if `Unit.symbol` values are ever renamed without a corresponding backfill of existing `Product.unit` values.

## 16. Business/accounting decision needed (logged during P2-2 implementation, 2026-07-18)

- **`src/services/orderFulfillmentService.ts` implements real FIFO/WAC (weighted-average-cost) stock-lot costing for order-delivery COGS, but has zero importers anywhere — it has never been wired into the live order-delivery path.** The live path (`utils/profitReportGeneration.ts`, invoked on every order marked `DELIVERED`) instead uses a static cost basis (the order item's snapshotted `costPerUnit`, falling back to the product's current `costPerUnit`/`basePrice`). FIFO/WAC costing is generally more accurate — it reflects what the specific units sold actually cost, accounting for cost changes over time across stock lots — whereas a static cost basis can misstate margin whenever purchase costs have changed since a product's current cost fields were last updated. **Not fixed as part of P2-2's profit-calculation consolidation, and deliberately not decided unilaterally**: switching the live costing method would change actual computed profit/COGS figures for real orders going forward, which is an accounting-methodology choice (which costing method the business uses and reports under — this can have tax/audit implications, not just an internal-code-quality one), not a pure engineering refactor. Recommend the business/finance stakeholder decide whether to switch to FIFO/WAC (in which case `orderFulfillmentService.ts` is most of the implementation already written) or keep the static-cost-basis approach and delete `orderFulfillmentService.ts` as dead code. Principal: the code already exists either way; the only remaining work is the decision plus wiring it in (if approved) or deleting it (if not).

## 21. Newly discovered items (logged during Principal Engineer Transition Phase 4 — standards-adoption audit, 2026-07-18)

An independent re-audit of `lib/error-handler.ts`/`lib/validation.ts`/`lib/paginationHelper.ts` adoption confirmed the existing "1 of 105 routes" figures from §17 are still exactly accurate (same single file, `categories/route.ts`, for both), and surfaced concrete, previously-unnamed instances of the risk that low adoption implies in the abstract:

- **Client-facing raw `error.message` leaks, confirmed in at least 5 routes**: `src/app/api/products/route.ts` and `src/app/api/upload/route.ts` return `details: error instanceof Error ? error.message : ...` directly in the JSON response on 500s; `src/app/api/seed/route.ts` and `src/app/api/admin/payouts/generate/route.ts` do the same; `src/app/api/admin/analytics/route.ts` is the worst instance — puts the raw message directly in the primary `error` field *and* derives the HTTP status by string-matching `error.message?.includes('Unauthorized')`, a fragile hand-rolled pattern that `lib/error-handler.ts`'s `AuthenticationError` class already exists to replace. Across the codebase, **40 of 105 route files** reference `error.message` inside a catch block; most echo it to the client via a `details`/`error` field rather than logging it server-side only. **Severity: Medium (information disclosure — CWE-209 class), not Critical** — no route was found leaking credentials or tokens this way, but internal error detail (which can include Prisma constraint/column names or other implementation detail) reaching an untrusted client is a real hardening gap, not a style nit. Principal: small — these 5 are a concrete, well-scoped batch (a few hours) to migrate onto `handleError`, ahead of the broader 104-route adoption effort. Deliberately not fixed in this pass — the Principal Engineer Transition's own scope explicitly excludes new code changes unless a critical defect is found, and this is assessed as medium, not critical; logged here as the top-priority slice of the existing `validation.ts`/`error-handler.ts` adoption backlog (§17) rather than actioned unilaterally.
- **Pagination gap, more precise than previously stated**: 8 files use `lib/paginationHelper.ts`; a separate 5 files (`admin/manual-sales`, `partner/profits`, `products`, `search/companies`, `search/products`) hand-roll their own `skip`/`take`; an unspecified further number of list-returning GETs (e.g. `categories/route.ts` itself) return a fully unbounded `findMany()` with no pagination at all. Not a new finding in kind (already tracked as part of §17's adoption gap), but this specific breakdown wasn't previously recorded.

This is an offline, human-invoked developer utility, not a production code path — low real-world risk (nothing automated pipes its output anywhere), but worth a quick fix (log only the decoded payload, never the raw token) the next time this script is touched. `scripts/migrate-user-passwords.js` similarly logs per-user emails (PII) during an offline migration run — same low-but-nonzero risk profile.

### ⚠️ Critical bug found and fixed during Phase 2 part 3's live verification: customer checkout was completely broken

**Severity: the highest-impact finding of this entire multi-phase initiative** — not a design gap or inconsistency, but a live-breaking defect in the platform's single most important code path. `POST /api/orders` (the customer-facing checkout endpoint — not the admin-created-order path, which was unaffected) passed `originalPrice`, `discountApplied`, and `finalPrice` into `OrderItem.create()`. **None of these three fields have ever existed on the `OrderItem` Prisma model**, confirmed by searching this repository's *entire* git history for both the schema file and the route file — they were never added, then removed; they were simply never real. Every real invocation of this endpoint against an actual database would fail with `Unknown argument 'originalPrice'` and return a generic 500 "Failed to create order."

**Why every existing test missed this**: every test covering this route (`order-creation.test.ts`, `order-stock-race-guard.test.ts`, `order-confirmation-email.test.ts`, etc.) mocks `@/lib/prisma` entirely — a mocked `create()` call accepts and returns whatever it's told to, with zero schema validation. A schema/code mismatch like this one is invisible to mocked unit tests by construction; it can only be caught by either (a) integration tests against a real database, of which this project has none for this route, or (b) exactly what surfaced it here — a human or agent manually exercising the live endpoint end-to-end. This is the concrete argument for why this session's discipline of live-verifying every new feature against the real dev/staging database (not just running the mocked test suite) matters: it doesn't just verify the new code, it occasionally catches something the entire existing test suite structurally cannot.

**Fix**: removed the three non-existent fields from the `orderItems.create` mapping in `src/app/api/orders/route.ts` (confirmed via grep that no other code anywhere reads `originalPrice`/`discountApplied`/`finalPrice` off a persisted `OrderItem` — the identically-named fields elsewhere in the codebase are all in-memory pricing-display utilities, unrelated to this model). New regression test asserts the exact shape sent to `OrderItem.create` so this specific class of error can't silently reappear.

**Open question for the product owner, not resolved here**: how long has this been broken, and has it caused any real lost orders in production? This fix only touched the code; it did not — and could not, from this session alone — determine whether any customers have been unable to complete checkout, or since when. Recommend checking production error logs/monitoring (if any exist) for `Unknown argument` or 500 rates on `/api/orders` as the immediate next step, independent of this codebase work.
